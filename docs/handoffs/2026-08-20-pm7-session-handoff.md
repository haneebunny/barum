## 3. 오늘 확정된 판정 수치 (발표에 쓸 수 있는 것 / 없는 것)

**오늘 하루의 핵심 발견: 우리가 재던 지표 상당수가 in-sample이었다.** 즉 고칠 때 쓴 데이터로 채점하고 있었다.

### 쓰면 안 되는 것

| 수치 | 이유 |
|---|---|
| 규칙 오탐 5 → 0 | 오탐 내는 후보를 계속 기각해온 결과. **회귀 감시용으로만 유효** |
| 증발 7 → 2 | 그 정답셋 문장을 보고 키워드를 넣었다. in-sample |
| 규칙 단독 위반탐지 8/16 | 규칙 자체가 이 셋으로 만들어졌다 |
| **62.5% → 81.0%** | 성능 개선이 아니라 **낡은 평가셋 교체**(측정 오차 제거) |
| **74.6% → 81.0%(A→B)** | 성능 개선이 아니라 **평가 배치 구성을 운영과 맞춘 것** |
| 검토필요 포착 63→106, 하드오탐 30→0 | 측정 도구가 **마지막 회차 값만** 찍고 있었다(수정됨, 재측정 안 함) |
| "위반의 43%" | 분모가 7건. 퍼센트로 쓰면 정밀도 과장. **"7건 중 3건"으로 쓸 것** |

### 쓸 수 있는 것 (성격 표현까지 지킬 것)

| 수치 | 표현 주의 |
|---|---|
| 문장 단위 안정성 90.5% (42문장 3회) | **"정확도"가 아니라 "재현성"** |
| 1차 필터 판정대상 통과 51~55 → 62/65 | 홀드아웃 119문장, 각 3회, 범위 비겹침. **"탐지율 개선"이라 부르면 안 됨** |
| 1차 필터 비대상 차단 21~22 → 22~23 | 범위 겹침 → **"유지됨"으로 기술** |
| 위조증빙 대조 위조 2건 격상/진짜 1건 오판 없음 | 표본 3건. **"성능"이 아니라 "동작 확인"** |
| 팩 미커버 87/148 | 발견 시점 값(과거형으로). 현재는 미등재 54(실질 32) |
| 규칙집 violation 53 / needs_review 24 | "감사 결과"가 아니라 **"규칙집 재분류 결과"** |

### 판단 기준 세 가지 (이 구분을 흐리면 과잉 교정이 난다)

- **개선 주장**("이만큼 좋아졌다") → in-sample이면 못 씀
- **발견의 근거**("이런 문제가 있었다") → in-sample이어도 씀. 표본 크기만 밝히면 됨
- **현재 상태**("지금 규칙집은 이렇다") → 세면 나오는 값이라 씀

실제로 포포가 맞는 수치(53/24)를 "출처 불명"이라며 뺀 사고가 있었다. **의심되면 빼기 전에 도도3에게 물어보라고 안내할 것.**

## 7. 오늘의 교훈 (다음 PM이 반복하지 말 것)

**(가) 표본을 안 보고 일반화하지 말 것.** PM7이 "안 읽은 이미지" 발견을 근거로 "오늘 나온 결론들의 의미가 달라진다"고 팀장께 보고했는데, 도도3이 세어보고 반박했다. 프롬프트 A/B는 홀드아웃에 2호가 0건이라 안 흔들리고, 규칙 천장은 팩 대조 결론이라 상품 입력과 무관했다. **발견이 커 보이면 그 크기를 다른 결론까지 확장하고 싶어진다.**

**(나) 작은 분모에 퍼센트를 붙이지 말 것.** 오늘만 세 번 걸렸다. 위반 16건(1건=6%p), "43%"(분모 7건), 나노바나나 거부율 17%(실제는 32회 중 1회로 3.1%).

**(다) 신호를 만들어놓고 안 읽는 패턴.** 도도 2대가 하루에 세 번 반복했다. 지표가 0건 움직였는데 넘어가고, "정답셋에 없으면 검증 불가"라고 직접 써놓고 그게 오탐에도 적용되는 걸 놓치고, 자기 탐침이 잡은 오탐을 "내가 지어낸 문장이 부실해서"라며 지웠다. **탐침이 걸리면 문장 탓하지 말고 더 자연스러운 문장으로 다시 잴 것.**

**(라) PM이 실측 없이 지시하지 말 것.** PM7이 베베의 A/B 실측치(7개→11개)를 그대로 "N개 모듈 안내를 만들라"고 냐냐에게 지시했는데, **그건 케이스 1건의 값이지 공식이 아니었다.** 냐냐가 "숫자를 지어내 보여주는 건 실측 없는 수치 표기와 같다"고 잡아줬다.

**(마) 팀원이 PM 판단을 교정하면 대체로 팀원이 맞았다.** 오늘 네 번 있었고 네 번 다 그랬다. 도도3의 "규칙 오탐 0건도 in-sample이다", 냐냐의 위 건, 도도3의 "needs_review를 규칙집에 두느냐 VLM에 맡기느냐가 한 단계 더 있다", 도도3의 일반화 반박.

**(바) 발표 서사는 "고도화 결과"가 중심이어야 한다.** "측정이 틀렸다"를 중심에 두면 팀장이 **"그래서 어쩌라고"**라고 반응한다. 같은 지적을 세 번 받았다([[barum-portfolio-narrative-rule]]).

**(아) 급하다고 먼저 머지하면 이어지는 작업이 유실된다.** PM7이 표 렌더 수정(PR #231)을 급하다고 먼저 머지했는데, 냐냐가 같은 브랜치에 렌더러 통합을 이어서 푸시하는 중이었다. PR이 닫혀 통합 커밋이 main에 안 들어갔고, 냐냐가 `git log`로 직접 확인해서 발견했다. **작업 중인 브랜치인지 먼저 물어볼 것.**

**(자) 리팩터링이 기존 취약점의 위험도를 올릴 수 있다.** `productName` escape 누락은 원래도 있었지만, export 파일에만 쓰일 때는 파일을 열어야 실행됐다. 렌더러 통합으로 `dangerouslySetInnerHTML` 경로가 생기면서 **앱 안에서 바로 실행되는 문제로 바뀌었다.** 렌더 경로가 바뀌는 변경에서는 기존 escape 처리를 다시 볼 것.
