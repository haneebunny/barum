## 1. 작업 A: score_eval.py 43문장 재검증 (작고 빠름, 먼저)

### 왜
지난 채점(Gemini 52.5% / GPT-5 62.5% / GPT-5-mini 65.0%)은 **4호→5호 리네임 전**, **레퍼런스 팩 반영 전**
숫자다. 그 뒤로 판정 프롬프트·라벨 체계·규칙집이 다 바뀌었는데 재실행을 안 했다. 발표에서 "몇 % 맞혀요"를
말하려면 지금 코드 기준 숫자가 필요하다.

### 할 일
```bash
cd backend
./venv/bin/python scripts/score_eval.py --dry        # 배선 점검(호출 없음)
./venv/bin/python scripts/score_eval.py               # 기본 provider(openai=GPT-5-mini)로 실채점
```
- 결과는 `data/eval_result_openai_<model>.xlsx` + 콘솔에 일치율·미탐·오탐 출력.
- 비교표 갱신하려면 `--provider gemini`로도 한 번 더 돌려서 `data/eval_compare.csv`에 누적.
- **미탐(위반을 합법/대상외로 놓침)이 1급 지표.** 이전보다 나빠졌으면 바로 PM에게 플래그(회귀 의심).
- 끝나면 `ROADMAP.md` §6 데이터 현황, `PROGRESS_BE.md`에 결과 기록.

### 알아둘 것
- `score_eval.py`는 **RagJudge를 안 거치고 VLM 프롬프트를 직접 호출**한다(순수 프롬프트 정확도 측정용,
  기존 방식 그대로 유지). RagJudge까지 포함한 end-to-end 정확도를 재려면 별도 하네스가 필요한데,
  그건 이번 작업 범위 밖이다. 필요하다고 판단되면 만들지 말고 PM에게 먼저 제안할 것(범위 확장은 하니 승인 필요).
- VLM 호출은 과금이다. 재시도 없이 실패 기록·스킵(이미 그렇게 구현돼 있음). 큰 배치 반복 실행 금지, 1~2회로 끝낼 것.

## 2. 작업 B: FR-14 수정 권고안 생성 (오늘의 메인, 착수조건 성립)

### 스펙 원문 (기획서 v1.9, FR 테이블. v1.8과 FR-14 문구 자체는 동일, 아래 §5 참조)
> **FR-14 · 수정 권고안 생성**. 목적: 탐지에서 끝내지 않고 안전한 대체 표현 제시.
> 입력: 탐지된 위반 문구, 관련 원료·조항. 처리: **위반 문구별로 위험을 낮춘 대체 표현을 조건표 기반으로 제안.
> 효능 주장은 창작하지 않고 안전 표기 틀 안에서만 제시하며, 확정 문구가 아닌 권고임을 명시.** 검증 리포트의
> 마지막 단계로 제공. 출력: 문구별 수정 권고안(대체 표현 후보). 우선순위: 상.
>
> (v1.7 변경로그) "서비스를 탐지 → 근거 → 수정 → 생성 하나의 흐름으로 재구조화. 수정 권고안 생성(FR-14) 신설."
> 착수 조건(§기획서): "핵심 판정 엔진(FR-4~6) 안정화 이후 착수". **이미 충족**(RagJudge·RAG grounding 완료).

### 핵심 제약 (읽고 설계할 것, 자유생성 아님)
**"조건표 기반으로 제안", "효능 주장은 창작하지 않고 안전 표기 틀 안에서만"**. 이 두 문장이 설계를 사실상
결정한다. LLM에게 "이 문구를 안전하게 고쳐줘"라고 자유롭게 시키는 방식이 아니라, **위반유형별/원료별로 미리
정의된 안전 표기 틀(조건표)에서 대체 표현을 골라 채우는 방식**으로 읽힌다(FR-11도 같은 원칙: "조건표로
결정적으로 처리, 창작하지 않음"). 이 조건표가 지금 `reference/cosmetic_kr/`에 **없다**. 있는 건 옛 식품
레퍼런스 쪽 `reference/violation_types/certified_phrases.md`("합법 인정문구")뿐인데, 화장품용이 아니라
구조 참고용으로만 볼 것.

### 착수 전 반드시 확인할 것 (CLAUDE.md A·B규칙 그대로 적용)
아래는 코드를 쓰기 전에 하니에게 선택지로 물어야 할 지점이다. 짐작으로 채우지 말 것:
1. **조건표를 어디서 가져오나**: 대수가 새로 저작(화장품법 위반유형별 안전 대체 표현 세트)해야 하는지,
   아니면 하니가 가진 자료가 있는지.
2. **응답 스키마**: `Finding`에 필드 추가(예: `Finding.suggestion`)로 `CheckReport` 안에 넣을지, 아니면
   별도 엔드포인트(`POST /remediate` 등)로 뺄지. "검증 리포트의 마지막 단계로 제공"이라는 문구는 전자에
   가깝게 읽히지만 확정은 하니가.
3. **원료 기반 매칭 재사용 범위**: FR-14 입력에 "관련 원료·조항"이 명시돼 있다. 2호(기능성오인) 판정에
   이미 있는 `reference/ingredients.py` 성분 정합 로직·`functional_ingredients.json`을 그대로 재사용할
   여지가 큼. 1호·5호는 재사용할 기존 조건표가 없어서 새로 설계 필요.
4. **"권고임을 명시"**: 프론트 쪽엔 이미 관련 문구가 목업에 들어가 있다("확정 문구가 아닌 권고" 톤).
   API 응답에도 disclaimer 필드나 고정 문구가 필요한지 확인.
5. **티어 게이팅 (v1.9에서 새로 확정, 2026-08-12)**: 기획서 v1.9 비즈니스 모델에 "무료는 탐지·근거
   체험, **수정 권고안(FR-14)은 Basic부터**"가 명문화됐다. 즉 `/check` 응답에서 `suggestion`(또는 별도
   엔드포인트)이 **모든 사용자에게 항상 나가면 안 된다.** 지금 프로젝트엔 로그인·계정·결제가 전혀 없어서
   (Out of Scope, 마이페이지는 단일 데모 계정으로만 시연) "티어를 어떻게 판별하나"부터 막힌다. 짐작 금지,
   하니에게 확정 필요:
   - 데모에서 티어를 어떻게 흉내내나 (요청 파라미터로 티어 지정? 데모 계정 고정 티어? 프론트에서만 UI로
     숨기고 백엔드는 항상 내려주나?)
   - FR-14 구현 자체는 그대로 진행하되, 게이팅 방식만 별도로 확인하고 붙이면 됨(구현을 막는 문제는 아님).

### 참고할 기존 코드
- `backend/src/barum/models.py`: `Finding`·`CheckReport` 스키마. 새 필드 추가 시 여기.
- `backend/src/barum/judge/cosmetic.py`: `RagJudge`가 이미 `legal_basis`·`flag`를 채우는 흐름. 같은 위치에서
  `suggestion`도 채울 수 있을지 검토.
- `backend/src/barum/reference/mapping.py`, `reference/ingredients.py`: 위반유형·근거조항·성분 정합 기존 로직.
- `reference/violation_types/certified_phrases.md`: 식품 도메인 "합법 인정문구" 선례(구조 참고용, 내용은 화장품에 안 맞음).

### 검증
- 순수 로직(조건표 매칭·템플릿 채우기)은 `pytest` 유닛테스트. VLM을 실제로 써서 대체 표현을 생성하는 경로가
  생기면 그 부분만 수동 스모크(과금 호출은 재시도 없이 실패 기록).
- 끝나면 `openapi.json`·`fixtures` 갱신, `docs/api/README.md`에 필드 문서화.
