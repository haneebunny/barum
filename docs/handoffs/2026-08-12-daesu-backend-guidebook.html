작업 B. FR-14 수정 권고안 생성

왜 하나: 지금은 "이 문구가 위반입니다"까지만 알려줍니다. FR-14는 거기서 한 걸음 더 나아가, "그럼 이렇게 고치세요"라고 안전한 대체 표현을 옆에 붙여주는 기능입니다. 아래는 설계가 전부 확정된 상태입니다. 하니에게 다시 물어볼 것 없이 그대로 구현하면 됩니다.

B-1. 스펙 원문 (기획서 v1.9, FR 테이블)

FR-14 · 수정 권고안 생성. 위반 문구별로 위험을 낮춘 대체 표현을 조건표 기반으로 제안. 효능 주장은 창작하지 않고 안전 표기 틀 안에서만 제시하며, 확정 문구가 아닌 권고임을 명시. 검증 리포트의 마지막 단계로 제공. 출력: 문구별 수정 권고안(대체 표현 후보).

v1.9 추가 확정사항: 수정 권고안은 무료 티어에 안 나가고 Basic부터 나갑니다. 오늘은 게이팅 없이 항상 채워서 구현하고, 티어 분기는 나중 작업으로 미룹니다(지금 로그인·계정 자체가 없어서 게이팅을 걸 데가 없습니다).

B-2. 설계 (자유생성 아님, 결정론적 템플릿 치환)

"조건표 기반", "창작하지 않음"이 설계를 결정합니다. LLM에게 "알아서 안전하게 고쳐줘"라고 시키지 않습니다. 대신 Finding.violation_type + Finding.flag 조합(이미 RagJudge가 채워주는 값이라 새로 뽑을 것 없음)으로 아래 §B-3 표에서 미리 써둔 문장을 골라 {span}만 채워 넣는 방식입니다. AI 호출이 아예 필요 없는 순수 문자열 치환입니다.

B-3. 조건표 (그대로 코드에 옮기면 됩니다)

키는 (violation_type, flag) 조합 5가지뿐입니다. {span}은 Finding.span으로 채웁니다. 모든 문장 끝에 disclaimer를 붙입니다.

violation_typeflag템플릿
1호_의약품오인위반'{span}' 표현은 의학적 효능이나 질병 치료를 암시해 화장품법상 대체 문구가 없습니다. 이 표현 자체를 빼고, 필요하면 보습·세정 등 화장품 본연의 기능으로만 서술하는 것을 권장합니다.
1호_의약품오인검토필요'{span}' 표현은 실증자료가 있으면 사용할 수 있습니다. 실증자료가 없다면 '~에 도움을 줄 수 있어요'처럼 확신도를 낮추거나, 표현을 빼는 것을 권장합니다.
2호_기능성오인위반'{span}' 표현이 주장하는 기능성 효과의 고시 원료가 확인되지 않습니다. 해당 효능 표현을 빼거나, 기능성 심사·보고를 받은 뒤 사용하는 것을 권장합니다.
2호_기능성오인검토필요'{span}' 표현과 관련된 성분은 확인되지만 기능성 심사·보고 여부는 확인할 수 없습니다. 심사·보고를 받았다면 그대로 사용 가능하고, 아니라면 'OO 성분 함유'처럼 일반 서술로 낮추는 것을 권장합니다.
5호_거짓과장기만위반'{span}' 표현은 구체적 근거 없는 단정적 수식어입니다. 표현을 빼거나, 객관적으로 확인 가능한 사실(수치·시험 결과 등)로 바꾸는 것을 권장합니다.

disclaimer (모든 문장 끝에 그대로 붙이기): (권고 예시이며 확정 문구가 아닙니다.)

이 5개 조합 밖(대상외·합법, 또는 예상 못 한 조합)은 suggestion = None으로 둡니다. 근거 없이 억지로 채우지 않습니다.

B-4. 스키마·구현 위치 (확정)

  • backend/src/barum/models.py의 Finding에 suggestion: str | None 필드 추가. 새 엔드포인트 안 만듭니다(스펙의 "리포트 마지막 단계로 제공"과 일치, 프론트도 기존 Finding 구조만 보면 됨).
  • 템플릿 딕셔너리는 새 파일 backend/src/barum/judge/remediation.py에 (violation_type, flag) -> str 매핑으로 둡니다. 함수 하나: suggest(finding: Finding) -> str | None.
  • backend/src/barum/judge/cosmetic.py의 RagJudge.judge()가 Finding을 다 채운 직후, 각 finding에 finding.suggestion = suggest(finding)로 채웁니다. PromptJudge·StubJudge에도 같은 방식으로 붙입니다(세 judge 다 똑같이 마지막에 한 줄 추가하는 정도).

B-5. 참고할 기존 코드

  • backend/src/barum/models.py: Finding, CheckReport 스키마 (suggestion 필드 추가 위치)
  • backend/src/barum/judge/cosmetic.py: RagJudge가 이미 legal_basis·flag를 채우는 흐름. 그 바로 다음 줄에서 suggestion도 채우면 됩니다.

B-6. 검증

  • tests/test_remediation.py 새로 만들어서, 5개 조합 각각 올바른 템플릿이 나오는지 + {span} 치환이 되는지 + disclaimer가 붙는지 + 5개 밖 조합은 None인지, pytest 유닛테스트로. AI 호출이 없는 순수 로직이라 목킹도 필요 없습니다.
  • 실제 이미지·문구로 /check 한 번 스모크(과금 소량, 1회만): 응답 JSON에 suggestion이 채워져 나오는지 눈으로 확인.

./venv/bin/python -m pytest tests/ -q

작업 C. OCR 방식 비교표 + 테스트셋 라벨링 (발표용, 여유되면)

왜 하나: 지금은 "이미지에서 글자를 먼저 읽고(1단계) → 그 글자를 판정(2단계)"하는 2단계 방식입니다. "VLM이 이미지를 통째로 보고 한 번에 판정"하는 방식도 있습니다. 발표에서 "우리는 왜 2단계를 골랐나"를 숫자로 보여주려고 두 방식을 비교합니다.

C-1. 무엇을 비교하나

  • ② 지금 방식: VLM이 글자 읽기 → 판정 (나눠서)
  • ③ 한 방: VLM이 이미지 통째로 읽고 바로 판정
  • (여유 더 있으면) ① 전용 OCR 엔진: 진짜 OCR 도구(무료 Tesseract 등)로 글자만 뽑고 → 판정. 비용·읽기정확도 한 줄만 참고용으로.

C-2. 비용 결론 (발표 톤 주의)

  • 지금 데모 규모에선 세 방식 다 비용이 사실상 0입니다. "한 방이 싸다"를 발표 헤드라인으로 걸면 안 됩니다.
  • 규모가 커지면 오히려 나눠서 하는 쪽(특히 전용 OCR)이 더 쌉니다. VLM에 이미지를 통째로 넣으면 비전 토큰이 비싸거든요.
  • 그래서 발표 메시지는 "비용"이 아니라 "정확도 + 어느 문구가 문제인지 정확히 짚어준다(설명 가능성)"로 갑니다. 이게 2단계 방식의 강점입니다.

C-3. 채점 정답 만들기 (제일 조심할 부분)

비교하려면 "이 이미지의 이 문장이 위반이다"라는 믿을 수 있는 정답이 있어야 합니다.

⚠️ AI가 만든 정답으로 AI를 채점하면 순환논리라 발표에서 공격당합니다. 그래서:
  1. 대수(AI)가 테스트 이미지 14장의 문장에 위반/합법 라벨 초안을 빠르게 만든다.
  2. 하니가 그 ~50문장을 검수·수정해서 확정한다. (14장이라 20~30분이면 끝남)
  3. 검수 전 라벨로 낸 숫자는 "잠정"이라고 표시한다.
발표에선 "라벨은 AI 초안 + 규칙집 만든 하니가 검수 확정"이라고 말하면 방어됩니다. 검수 잣대는 이미 확정된 경계표현 기준(진정=검토필요, 탄력·민감=합법 등, docs/handoffs/2026-08-11-backend-session-handoff.md §3).

테스트 데이터 위치:

  • 이미지 14장: backend/11st_probe_cosmetic/read_test/images/
  • 글자 읽기 정답 초안: backend/11st_probe_cosmetic/read_test/_llm_answer_key.json, 사람 검수용 빈 템플릿: worksheet_blank.md

D-3. "피지감소" 동의어 매칭 안 됨 (바로 반영)

D-4. "모공수축" 판정 규칙 확정 (하니 결정, 바로 반영)

공통 규칙 (작업 내내 지킬 것)

Git (AGENTS.md)

  • main에 직접 push 절대 금지. 항상 feature/be-... 브랜치 → PR → 하니가 머지.
  • git add . 절대 금지. 여러 사람이 같은 폴더에서 동시에 작업 중이라, 전체 추가하면 남의 파일이 딸려 들어갑니다. 항상 파일을 지정해서 git add <파일>.
  • PR 리뷰어는 haneebunny. gh CLI가 없어서 PR은 push 후 뜨는 링크를 하니에게 주면 하니가 웹에서 만듭니다.
  • 새 작업은 항상 최신 main에서 브랜치를 새로 땁니다.

돈 (API 호출)

  • 판정·OCR은 과금 호출입니다. 재시도하지 않습니다. 실패하면 기록하고 넘어갑니다.
