# 실증자료·설문 파일 업로드 (2026-08-25)

> 발단: create 모드에서 실증자료·설문을 한 칸씩 손으로 치는 게 번거롭다는 지적.
> 전성분은 이미 파일 업로드 경로가 있는데(`/uploads/ingredients`, 2026-08-24)
> 실증자료·설문엔 그 경로가 아예 없었다.

---

## 1. 규모 확인부터

먼저 얼마나 번거로운지 셌다.

```
실증자료(ClinicalEvidence)  5칸 × 자료 수
설문조사(SurveyEvidence)    6칸 × 설문 수   ← 6칸 전부 필수
```

각 2건이면 22칸이다. 전성분(40~60칸)의 절반쯤이지만 무시할 양은 아니다.

**진짜 문제는 칸 수가 아니라 경로의 부재였다.** 전성분엔 Dropzone이 있고
실증자료·설문엔 점선 버튼 하나뿐이라, 사용자는 `+ 추가`를 눌러보기 전까지
무슨 칸이 있는지도 모른다. 설문이 6칸 필수라는 사실도 버튼을 눌러야 보인다.

## 2. VLM은 검토하고 접었다

처음엔 시험성적서 PDF·이미지를 OCR로 읽는 방향을 팠다. 접은 이유가 셋이다.

| | |
|---|---|
| 규모 불일치 | 자동으로 채울 칸이 6개인데 PDF 렌더링 + VLM 파이프라인을 새로 놓는 건 과잉 |
| 비용·실패 | 성적서는 20~50페이지다. 전부 태우면 페이지 수만큼 과금되고, 이 프로젝트는 VLM 호출을 재시도하지 않는다(CLAUDE.md E) |
| 위험 구간 | `claim`·`value`는 성적서에 그 문장으로 없다. "멜라닌 지수 12.3% 감소"를 "다크스팟 개선 87%"로 옮긴 건 사업자의 마케팅 번역이고, **그 번역 구간이 과대광고가 태어나는 자리**다. 기계를 넣을 곳이 아니다 |

대신 **전성분과 같은 순수 파싱**으로 갔다. VLM·LLM 호출 0회다.

## 3. 두 샘플 파일이 설계를 정했다

실제로 제공된 파일 둘이 서로 달랐다.

```
임상실험.txt   탭 구분, 헤더 있음, 2행
  무엇을 개선했나(claim) │ 결과 수치(value) │ 시험기관명(institution) │ ...
  다크스팟 개선          │ 87%             │ 유어랩 피부과학연구소     │ ...

설문조사.txt   탭 구분, **헤더 없음**, 1행
  발림성 만족 │ 94% │ 150명 │ 유어리서치 │ 2026년 3월 │ 온라인 자기기입식 설문
```

탭 구분인 걸 보면 엑셀·시트에서 복사해 붙인 것이다. 그래서 `.xlsx`도 같이 받는다.

**전성분 파서를 그대로 못 쓰는 이유가 여기 있다.** 전성분은 헤더 이름으로만
열을 잡는데(`_find_header`), 그러면 설문 파일은 통째로 못 읽는다. 그렇다고
열 순서를 고정하면 순서가 다른 파일이 조용히 잘못 들어간다.

### 3단으로 잡는다

| | 방법 | 두 샘플에서 |
|---|---|---|
| 1 | **헤더 이름.** 첫 행에서 필드 라벨이 2개 이상 잡히면 헤더로 본다 | 임상 5칸 전부 |
| 2 | **값의 생김새.** `%`·`배`→수치, `명`→인원, `8주`→기간, `연구소`·`리서치`→기관, `설문`·`온라인`→방법 | 설문 6칸 전부 |
| 3 | **고정 순서 폴백.** 남은 필드만 모델 정의 순서로 | 해당 없음 |

**2·3단으로 읽었으면 반드시 `warnings`를 낸다.** 여기서 열이 한 칸 밀리면
시험기관 자리에 시험기간이 들어간 채로 상세페이지까지 간다.

열 순서를 뒤집어도 제자리를 찾는다(테스트로 확인).

### 함정 둘, 미리 막았다

**`value="4주 후 2.1배"`가 `period`를 가로챈다.** 이건 가정이 아니라
`2026-08-24_실증자료_구조화.md` §2에 박힌 실제 표기다. 기간 판정기에 `^...$`
앵커를 걸어 단독 표기("4주")만 잡게 했다.

**1행짜리 헤더 없는 파일을 헤더로 오인하면 전량 유실된다.** 설문 샘플이 정확히
그 경우다. 데이터가 한 줄뿐이라 오인 = "0건 입력됨"이고 사용자는 이유를 모른다.
그래서 헤더 판정 문턱을 2개로 뒀다(`_HEADER_MIN_HITS`).

## 4. 테스트가 잡은 버그 둘

둘 다 수정 전 코드에서 실패하는 걸 확인하고 고쳤다.

**ㄱ. `line.strip()`이 선행 탭을 지워 열이 한 칸 밀렸다.**
첫 칸이 빈 행(`"\t2.1배\t..."`)에서 `claim` 자리에 `value`가 들어갔다. 빈 필수
항목이 안 보이고 엉뚱한 값이 실린다. 줄 끝만 떼도록 고쳤다.

**ㄴ. 헤더가 일부만 있을 때, 나머지를 형태로 추측해놓고 아무 말도 안 했다.**
1단으로 확정한 열만 안전한데 경고가 3단(폴백)에만 붙어 있었다. 헤더로 확정하지
않은 열은 전부 알리게 바꿨다.

경고 문구도 한 번 다듬었다. `claim`은 고유한 형태가 없어 **설계상 늘 폴백으로**
떨어지는데, 그때마다 "판단하지 못했다"를 붙이면 매번 뜨는 경고가 되어 정작 봐야
할 때 안 읽힌다. 배치 전체를 보여주는 것으로 갈음했다.

## 5. 곁다리로 드러난 것: 입력칸이 카드 밖으로 밀려나 있었다

업로드가 행을 즉시 채우자 겹침이 화면에 나왔다.

`<input>`은 기본 고유폭(`size=20`, 약 180px)이 있고 flex 자식의 `min-width`는
기본이 `auto`라 그 아래로 안 줄어든다. 2단 레이아웃에서 우측 카드가 좁아지면
칸이 카드 밖으로 밀려난다.

```
실증자료 행 :  [flex-1 시험기관명] [w-130px 시험기간]    180 + 130 = 310
설문조사 행 :  [flex-1 표본수]     [flex-1 조사기관명]   180 + 180 = 360  ← 두 개라 더 심함
```

### 전/후 실측 (초과 폭, px)

| 뷰포트 | 카드 폭 | 전성분 | 실증자료 | 설문조사 |
|---|---|---|---|---|
| 1280 | 478 | 0 | 0 | 0 |
| 1000 | 338 | 초과 | **4** | **51** |
| 900 | 288 | **34** | 초과 | 초과 |
| 860 이하 | 767~ (1단) | 0 | 0 | 0 |

수정 후 위 전부 0이다. `flex-1` 입력 8곳에 `min-w-0`을 넣었다.

**이건 이번 변경이 만든 버그가 아니다. 이번 변경이 드러냈다.** 세 블록 다
빈 배열로 시작해서(`useState([])`) `+ 추가`를 누르기 전엔 입력칸이 하나도
안 그려졌다. 아무도 이 화면을 본 적이 없었다.

> 입력할 UI가 없어서 정상 입력 경로를 아무도 테스트한 적이 없었다
> (`page.tsx`, 2026-08-23 제형·용량 건에 이미 같은 문장이 있다)

같은 함정을 두 번째 밟았다. **초기 상태가 빈 배열인 입력 블록은 실제로 행을
그려놓고 좁은 폭에서 한 번 봐야 한다.**

## 6. API

```
POST /uploads/clinical   multipart, 필드명 file
POST /uploads/survey     multipart, 필드명 file

200: {"rows": [...], "warnings": [...]}
415 지원하지 않는 확장자/형식   422 빈 파일·파싱 불가   413 5MB 초과
```

저장하지 않는다. 파싱 결과만 즉시 돌려주고 프론트가 폼에 채운다.

**설문은 6칸이 다 안 차도 행을 버리지 않는다.** 사용자가 폼에서 마저 채울 수
있어야 하고, 어느 칸이 비었는지는 `warnings`에 있다. 최종 판정은 기존
`isSurveyEvidenceComplete`가 한다.

이어붙일지 갈아끼울지는 전성분이 정한 규칙을 그대로 따랐다. 손입력 행이
채워져 있으면 이어붙이고, 비어있으면 교체한다.

- 새 유닛테스트 20개 + API 테스트 9개
- 백엔드 전체 871 통과. 실패 1건(`test_image_cache`)은 워크트리에 `.env`가 없어
  Gemini 키를 못 찾은 것으로 이번 변경과 무관
- 실제 파일 두 개를 브라우저에서 드롭해 16칸이 제자리에 들어가는 것 확인.
  콘솔 에러 0, 타입체크 0
- 겹침은 6개 뷰포트 폭에서 전후 실측

## 8. 남은 것

- **세로로 떨어진 붙여넣기.** PDF에서 긁으면 한 항목이 한 줄씩 세로로 떨어지는
  경우가 있다. "한 줄 = 한 건" 가정이 깨진다. 실물을 못 봐서 미뤘다
- **입력 폼 자체의 UX.** 초기 행 0개, `+ 추가`를 눌러야 칸이 보임, 한 건 채우고
  다음으로 갈 때 마우스로 손이 가는 문제. 이번 스코프에서 뺐다
- **설문 집계값.** 리서치사 엑셀은 응답자별 raw data이고 "96%" 같은 집계값은
  PPT 안에 있다. 우리가 계산해주면 "화면에 뜨는 수치 = 사업자가 친 수치"가
  깨진다. 손대지 않는다
