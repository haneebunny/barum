# 테스트가 유료 API를 부르던 문제 (2026-08-24)

> 담당: 백엔드6. PM이 "돈이 새고 있다"로 최우선 배정.
> `pytest tests/`를 한 번 돌릴 때마다 실제 Gemini 과금이 나가고 있었다.

---

## 1. 무엇이 새고 있었나

전체 스위트에 가드를 걸고 측정한 결과다.

| 호스트 | 테스트 수 |
|---|---|
| `generativelanguage.googleapis.com` (유료 Gemini) | 7 |
| `api.smith.langchain.com` (트레이싱) | 5 |

스위트 실행 시간의 대부분이 이 대기였다. **78초 → 9.65초**로 줄었다. 68초를
바깥 호출에 쓰고 있었다.

---

## 2. 측정 방법을 바꾼 이유

처음 제안된 방법은 소켓을 후킹해 **집계만** 하는 것이었다. 정확하지만 문제가 둘 있다.

1. **측정하는 2분 동안 또 실제 호출이 나간다.** 돈이 새는 걸 재는 데 돈을 쓴다.
2. 반대로 "차단하고 깨지는 테스트를 찾는" 방법도 안 된다. **차단만 하고 돌렸더니
   807개가 전부 통과했다.** 이 코드베이스는 예상된 실패를 의도적으로 삼키기
   때문이다(CLAUDE.md: 이미지·크롤 실패는 스킵하고 배치를 계속한다). 실패로는
   한 건도 안 드러났다.

그래서 **차단과 집계를 같은 가드에서** 한다. 지출 0으로 완전한 명단을 얻는다.

---

## 3. 진짜 원인: 테스트가 개발자 `.env`를 물려받는다

`JUDGE_KIND="stub"`으로는 못 막는다는 건 알려져 있었는데, 왜인지는 안 밝혀져
있었다. 스택을 찍어보니 이렇게 나왔다.

```
_generate_improve_content → build_image_plan → generate_module_images
→ vlm.py:355  self.client.interactions.create      ← 진짜 Gemini 이미지 생성
```

**이미지 생성이었다.** `JUDGE_KIND`는 판정기만 가짜로 바꾼다.

이미지 생성은 `IMAGE_GENERATION_ENABLED=1`일 때만 도는데, `.env`에 그 값이 있었다.
barum 코드는 여러 곳에서 `load_dotenv()`를 부른다(`vlm.py` 4곳, `storage`, `api`).
그래서 **`pytest`를 돌리면 개발자 `.env`가 그대로 테스트 설정이 된다.**

결과적으로 **테스트 동작이 누구 기계에서 돌리느냐에 따라 달라졌다.** 플래그를
켜둔 사람은 돈을 쓰고, 안 켜둔 사람은 안 쓴다. 재현이 안 되는 종류의 문제다.

---

## 4. 무엇을 바꿨나

### (1) `.env` 중화 — 원인 제거

`load_dotenv()`는 기본이 `override=False`다. **conftest에서 먼저 넣어두면 `.env`가
못 덮는다.** barum 임포트보다 위에서 넣는다.

```python
_TEST_ENV_DEFAULTS = {
    "IMAGE_GENERATION_ENABLED": "0",
    "LANGSMITH_TRACING": "false",
    "LANGCHAIN_TRACING_V2": "false",
}
```

진짜로 이미지 생성을 켜서 확인하는 테스트는 이미 `monkeypatch.setenv`로 켜고
`get_image_generator`를 가짜로 갈아끼우고 있었다. 그대로 동작한다.

### (2) 소켓 가드 — 재발 방지

로컬이 아닌 **모든** 연결을 막는다. 유료 호스트 목록을 손으로 관리하면 새 서비스가
붙을 때마다 다시 샌다.

조용히 통과시키지 않고 **실패**시킨다. 그리고 막힌 시도를 호스트·테스트별로 모아
세션 끝에 명단으로 찍는다. 예외를 삼키는 코드를 지나면 실패로 안 드러나기 때문에,
집계가 없으면 가드가 있어도 유출을 못 본다.

- `BARUM_TEST_ALLOW_NETWORK=1` — 수동 스모크용 탈출구. CLAUDE.md가 크롤·VLM은
  목킹하지 말고 수동 스모크로 확인하라고 해서 그 경로는 살려둔다.
- `BARUM_TEST_TRACE_NETWORK=1` — 막힌 호출의 출처를 스택으로 찍는다. 이번에
  원인을 찾은 방법이고, 삼켜지는 예외라 이게 없으면 출처를 알 방법이 없다.

### (3) 마지막 한 곳 — `test_image_cache.py` (다른 세션이 이미 고침)

`run_check`를 감싸면서 **진짜 함수에 위임**해 실제 OCR이 돌고 있었다. 측정 시점
(`945dcdd`)엔 그 상태였는데, **PR #362에서 이미 같은 방향으로 고쳐졌다**(진짜 위임
제거 + 고정 `CheckReport` 반환). 리베이스하면서 그쪽 수정을 그대로 받았다.

두 수정의 차이는 `n_sentences` 값 하나였다(#362는 1, 내 초안은 0). 처음엔 **0이
"OCR 전부 실패" 신호라서 내 값을 쓰면 캐시 폐기 규칙(#362)에 걸려 테스트가 깨진다**고
적었는데, **그건 틀렸다.** 캐시 폐기는 `n_ocr_failed_tiles`만 본다
(`checks_store.py` `_ocr_failed_count`). `n_sentences`를 실패 신호로 읽는 코드는
저장소에 없다. 실제로 `n_sentences=0`으로 바꿔 돌려봐도 7개가 다 통과한다.

main 버전을 취한 건 맞았지만 이유가 달랐다. **위험해서가 아니라 이미 머지된 쪽이라
충돌을 안 만드는 게 맞아서**다.

그래도 남길 원칙은 있다. **같은 문제를 동시에 고칠 때, 겉보기에 같은 수정이라도 그
사이에 들어온 규칙을 확인해야 한다.** 다만 그 확인은 **그 규칙이 실제로 무슨 필드를
읽는지 찍어보는 것**이어야 한다. 이번엔 그걸 안 하고 상호작용을 가정했고, 그래서
없는 위험을 있다고 적었다.

### (4) 가드 자체의 테스트

가드가 조용히 깨지면 그날부터 다시 샌다. 자가 테스트 5개를 넣었다(이름 차단·
IP 직결 차단·로컬 허용·에러 메시지에 대처법 포함·유료 플래그 기본 꺼짐).

자가 테스트는 예약 주소(`.invalid`, `192.0.2.0/24`)만 쓰고, 유출 명단에서는 제외한다.
진짜 유출과 헷갈리면 안 된다.

## 6. 남은 것

- **`test_image_cache.py`는 #362가 이미 고쳤다.** 이 문서의 측정은 그 전 시점이다.
- **크레딧 소진 자체는 별개 문제다.** 429가 뜨는 동안 `/check`는 "위반 0건 +
  이미지 일부를 못 읽었습니다"로 나온다. 코드 버그가 아니라 OCR이 전부 실패해서
  읽은 문장이 0개인 것이다. 충전하면 해소된다.
- **429일 때 화면이 "위반 0건"으로 보이는 건 위험하다.** 사용자가 "문제 없음"으로
  읽는다. 읽은 문장이 0개면 판정 결과를 내지 말고 실패로 표시하는 쪽이 맞아 보이는데,
  UI 변경이라 별도 논의가 필요하다.
