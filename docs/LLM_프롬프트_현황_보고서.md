> 응답 예시를 기록한다. 나중에 프롬프트 엔지니어링할 때 "전(개정 전)" 기준점으로 쓰기 위한 문서라, 코드가

## 0. LLM 호출 지점 한눈에

| 지점 | 파일 | 모델(기본) | 입력 | 목적 |
|---|---|---|---|---|
| OCR | `preprocess/ocr.py` | Gemini(`GOOGLE_API_KEY`) | 이미지(타일 PNG) | 상세페이지 이미지 → 문장 추출 |
| 판정(제로샷) | `judge/cosmetic.py` `PromptJudge` | GPT-5-mini(`OPENAI_API_KEY`) | 문장 배치(텍스트) | 위반유형 라벨링 |
| 판정(그라운딩, 기본 배포) | `judge/cosmetic.py` `RagJudge` → 내부 `PromptJudge`+context | GPT-5-mini | 규칙 미매칭 문장만 | 규정 grounding해서 판정 |
| 콘텐츠 생성(저위험 서술) | `generate/content.py` `generate_sections` | GPT-5-mini(`GENERATE_PROVIDER`, 없으면 판정 provider 재사용) | 제품정보(제품명·전성분·추가정보) | 제품개요·사용법·주의사항 생성 |

공통 어댑터: `vlm.py`의 `VLM` 프로토콜(`generate_json(prompt, images) -> dict`) 하나로 provider를 감싼다. 전부 **JSON
강제 출력**(OpenAI는 `response_format={"type":"json_object"}`, 거부하는 모델이면 없이 재시도), **재시도 없음**(과금
호출이라 실패하면 그 배치/문장만 스킵하고 기록), **배치 처리**(판정·OCR 둘 다 여러 항목을 한 번에 묶어 호출수 절감).

## 1. 판정(Judge) — 언제 RAG(그라운딩)를 먹이는가

이게 제일 중요한 지점이라 자세히 적는다. 판정은 3단으로 되어 있다.

```
문장 하나
  │
  ▼
① 규칙집 대조 (reference/rules.py, match_rule) — LLM 호출 없음, 결정론적
  │
  ├─ legal_allow 확정 → finding 없음, 끝 (LLM에 절대 안 감)
  ├─ violation/needs_review 확정 → finding 확정, 끝 (LLM에 절대 안 감)
  └─ 매칭 없음(규칙집에 없는 표현) → ② 로 감
                                        │
                                        ▼
② RAG 그라운딩 컨텍스트 조립 (reference/context.py)
   규정 5개 md + cases.md(실사례) 통째 인라인 (또는 사례만 pgvector 검색으로 교체)
                                        │
                                        ▼
③ PromptJudge에 context로 주입 → LLM 호출(그라운딩 있음)
```

**규칙이 이미 확정한 문장은 LLM을 아예 안 부른다.** RAG는 "규칙집에 없는, 애매한 표현"에만 먹인다. 이게 `RagJudge`
(배포 기본, `JUDGE_KIND=rag`)의 핵심 설계고, `judge/cosmetic.py:351` `RagJudge.judge()`에 그대로 있다.

### 1-1. 규칙 매칭 예시 (LLM 안 씀, 참고용)

```python
match_rule("진정 효과가 뛰어난 크림입니다")
# → needs_review, span="진정", 1호_의약품오인 (실증대상, LLM 안 감)
match_rule("탄력 있는 피부를 만들어줍니다")
# → legal_allow, span="탄력" (합법 확정, LLM 안 감)
match_rule("아토피 피부에도 좋은 재생크림")
# → violation, span="아토피", 1호_의약품오인 (위반 확정, LLM 안 감)
```

### 1-2. 그라운딩 컨텍스트 조립 (`reference/context.py`)

`build_judgment_context()`가 아래 문서를 **원문 그대로, 파생 가공 없이** 이어 붙인다(순서 고정):

1. `prohibited_expressions.md` — 금지·주의 표현 목록(T1~T6 라벨)
2. `violation_types/type_1_drug_misperception.md`
3. `violation_types/type_2_functional_misperception.md`
4. `violation_types/type_5_deception.md`
5. `functional_ingredients.md` — 기능성 고시원료표
6. `cases.md` — 실제 적발사례 (Phase1: 통째 / Phase3: `case_retriever` 있으면 판정할 문장 기준 유사 top-K 검색으로 교체)

벡터검색이 아니라 **통째 인라인**이 기본이다(코퍼스가 작아서 충분, PM 확정 사항). 실측 컨텍스트 길이: **22,014자**
(cases.md 포함, 2026-08-12 기준 레퍼런스 팩 스냅샷).

`PromptJudge._build_prompt()`가 context 유무로 프롬프트를 바꾼다:

```python
def _build_prompt(self, numbered: str) -> str:
    base = JUDGE_PROMPT.format(items=numbered)
    if not self.context:
        return base
    return (
        "아래 [판정 근거]는 화장품법 규정·판정기준·실제 적발사례다. "
        "반드시 이 근거에 비추어 판정하라.\n\n"
        f"[판정 근거]\n{self.context}\n\n"
        f"[판정 지시]\n{base}"
    )
```

즉 **켜고 끄는 스위치는 `context` 파라미터 하나**다. `PromptJudge(vlm, context="")`가 순수 제로샷,
`PromptJudge(vlm, context=build_judgment_context())`가 그라운딩. `RagJudge`는 매 `judge()` 호출마다 내부적으로
후자를 구성해서 쓴다(문장마다 검색 결과가 달라질 수 있어서 매번 새로 만듦).

### 1-3. 판정 프롬프트 원문 (`JUDGE_PROMPT`, `judge/cosmetic.py:148`)

score_eval.py와 공유하는 원본이다.

```
너는 한국 화장품 광고 문구가 화장품법 표시·광고 규정을 위반하는지 판정한다.
아래 문장 각각에 라벨 하나와 짧은 근거를 매겨라.

라벨(정확히 이 중 하나만):
- 합법 : 일반 보습·사용감·제형 설명 등 위반 소지 없음
- 1호_의약품오인 : 질병·치료·재생·염증 등 의학적/의약품 같은 효능 암시
- 2호_기능성오인 : 미백·주름개선·자외선차단 기능성 효능을 주장
- 5호_거짓과장기만 : 근거 없는 수치·최상급·비교우위·후기 단정·경쟁사 비방
- 대상외 : 광고 문구가 아님(성분명 나열, 거래·배송 안내, 인증서 표시, 단순 제품정보·브랜드명)

규칙:
- 한 문장에 여러 개 해당하면 가장 무거운 것 하나. 우선순위 1호 > 2호 > 5호 > 합법.
- 미탐(위반을 합법으로 놓침)이 제일 나쁘다. 애매하면 위반 쪽으로 판단한다.

문장:
{items}

JSON으로만 답하라: {"results": [{"n": 1, "label": "...", "reason": "..."}]}
```

`{items}`는 `"0. 문장1\n1. 문장2\n..."` 형태로 전역 번호를 매긴 배치(기본 `batch_size=12`)다. 번호로 결과를 되짚고,
개수가 안 맞으면(모델이 항목을 빠뜨리면) 위치 매칭을 포기하고 **미판정**으로 남긴다(합법으로 삼키지 않음, recall 우선).

### 1-4. 실제 전/후 비교 (같은 문장, 그라운딩 유무만 다름)

문장: `"약국 입점 화장품입니다"` (규칙집 미매칭 → 반드시 LLM으로 감, 그래서 비교에 적합)

**① 그라운딩 없음 (base PromptJudge, `context=""`)**

```json
{"위반유형": "1호_의약품오인", "플래그": "위반",
 "근거": "'약국 입점'이라는 표현은 소비자에게 의약품·의학적 신뢰성·효능으로 오인될 우려가 있어 의약품 오인 표시에 해당할 수 있음."}
```

**② 그라운딩 있음 (RagJudge fallback, `context=build_judgment_context()`)**

```json
{"위반유형": "5호_거짓과장기만", "플래그": "위반",
 "근거": "'약국 입점'은 특정 의료기관·약국과의 지정·연계·추천을 암시하는 표현으로 금지됨(화장품 표시·광고 관리지침 별표1 제시 예시·제13조 관련, 병원용·약국전용 표방 해당)."}
```

**차이**: 라벨이 1호(의약품오인)에서 5호(거짓과장기만)로 바뀌었고, 근거에 **실제 조문·별표 번호(제13조, 별표1)를
인용**한다. 그라운딩 없이는 모델이 그럴듯하게 추론만 하고, 있으면 규정 문서를 실제로 참조해서 근거를 댄다.
(참고: 라벨 자체는 모델 stochasticity로 호출마다 갈릴 수 있다. 2026-08-12 40문장 배포 평가셋 집계 기준으로는
"약국 입점"을 base 제로샷은 놓치고 RagJudge가 잡은 사례로 `PROGRESS_BE.md` 2026-08-12 항목에 기록돼 있다 —
단발성 예시보다 그 집계가 통계적으로 더 신뢰할 만하다.)

프롬프트 길이: 그라운딩 없음 기준 약 700자, 그라운딩 있음은 **22,594자**(그라운딩 블록이 프롬프트의 97% 이상을
차지). 프롬프트 엔지니어링 시 이 크기 차이가 지연시간·비용에 직결된다는 점 참고.

### 1-5. 2호(기능성오인)는 LLM 판정 뒤에 **코드가 한 번 더 개입**한다

`_functional_evidence()`(`judge/cosmetic.py:168`)가 LLM이 "2호_기능성오인"이라고 라벨링한 문장에 대해, 전성분표를
결정론적으로 대조해서 `flag`를 덮어쓴다(LLM은 "미백/주름/자외선차단을 표방했다"까지만 판단, 실제 고시원료가
있는지는 코드가 정확 조회로 확인). 실제 예시(그라운딩 없음 케이스, 문장 "약국에서만 판매하는 진정 크림,
미백에 도움을 줍니다", 전성분 미입력):

```json
{"위반유형": "2호_기능성오인", "플래그": "검토필요",
 "근거": "'미백에 도움을 줍니다'는 미백이라는 기능성 효능을 암시하는 표현으로, 기능성 화장품 여부를 입증하지 않으면 기능성 오인에 해당함. (전성분 미입력, 성분 정합 확인 못 함)"}
```

괄호 안 "(전성분 미입력...)"이 LLM 출력이 아니라 `_functional_evidence()`가 붙인 코드 생성 문구다. 이 문장은
1호(약국) 후보도 되는데 이 프롬프트는 "한 문장당 라벨 하나"라 모델이 어느 쪽을 골랐는지에 따라 놓치는 유형이
생길 수 있다 — 프롬프트 엔지니어링할 때 "복수 위반유형 동시 판정" 여지를 검토할 만한 지점.

## 2. 콘텐츠 생성(create/improve) — 저위험 서술 프롬프트

`generate/content.py` `_SECTION_PROMPT`. 판정 프롬프트와 별개로, **효능·기능 표현을 아예 못 쓰게 프롬프트 레벨에서
금지**하고 제품개요·사용법·주의사항만 쓰게 한다(효능 문구는 improve 모드는 조건표 치환, create 모드는 인증서-인정문구
매칭으로 별도 처리 — 이 LLM 호출과는 무관, 자유창작 금지 원칙).

```
너는 화장품 상세페이지의 '저위험 서술'만 작성한다.
효능·기능·치료·미백·주름·질병 관련 표현은 절대 쓰지 마라(그건 별도 처리된다).
아래 제품 정보로 제품개요·사용법·주의사항만 담백하고 사실적으로 써라.

제품명: {product_name}
전성분: {ingredients}
추가정보: {notes}

JSON으로만 답하라: {"제품개요": "...", "사용법": "...", "주의사항": "..."}
```

실제 호출 예시(제품명 "글로우 세럼", 전성분 "정제수, 나이아신아마이드, 글리세린", 추가정보 "민감성 피부용
저자극 라인"):

```json
{
  "제품개요": "정제수, 나이아신아마이드, 글리세린을 주성분으로 한 세럼입니다. 투명한 액상 제형으로 가벼운 사용감을 제공하며, 민감성 피부용 저자극 라인으로 개발되었습니다. 향료·색소 등 상세 성분 정보는 제품 포장을 확인하십시오.",
  "사용법": "세안 및 기본 스킨케어(토너) 후 적당량을 덜어 얼굴 전체 또는 필요한 부위에 고르게 펴 바릅니다. 흡수될 때까지 가볍게 두드린 후 다음 단계의 제품을 사용하십시오. 사용량은 개인별로 조절하세요.",
  "주의사항": "상처가 있는 부위에는 사용하지 마십시오. 사용 중 붉어짐, 가려움, 자극 등 이상이 생기면 사용을 중단하고 필요 시 전문가와 상담하십시오. 눈에 들어갔을 경우 즉시 깨끗한 물로 씻어내십시오. 제품 표기된 사용기한 및 보관 방법을 확인하고 직사광선과 고온을 피해 서늘한 곳에 보관하시며, 어린이의 손이 닿지 않는 곳에 보관하십시오. 특정 성분에 알레르기가 있는 경우 전성분을 확인한 후 소량으로 패치 테스트를 권장합니다."
}
```

효능·기능 표현이 실제로 안 섞여 나온 것 확인(금지 지시가 먹힘). 이 출력은 이후 `remove_pii()`로 PII 제거, `/check`로
재검증까지 거친다(코드가 LLM 출력을 무조건 신뢰하지 않음).

실패 시 폴백(과금 호출 실패, 재시도 없이 즉시 폴백):

```
[제품개요] {제품명}은(는) 일상 사용에 적합한 화장품입니다.
[사용법] 적당량을 덜어 피부에 부드럽게 펴 발라 줍니다.
[주의사항] 개봉 후 가급적 빠르게 사용하고, 사용 중 이상이 있으면 사용을 중단하세요.
```

## 3. OCR — 이미지에서 문장 추출

`preprocess/ocr.py`. 단일 이미지용(`OCR_PROMPT`)과 여러 타일 배치용(`BATCH_PROMPT`) 두 버전이 있다(같은 규칙,
배치는 이미지별로 결과를 나눠 받게 스키마만 다름).

```
이 이미지는 한국 이커머스 상품 상세페이지의 일부다.
이미지에 보이는 모든 한국어 텍스트를 위에서 아래 순서로 읽어라.

규칙:
- 광고 문구를 **문장 단위**로 끊어서 배열에 담는다.
- 줄바꿈은 문장 구분이 아니다. 디자인상 줄이 나뉜 한 문장은 하나로 합쳐라.
- 가격·배송·교환/반품 안내·회사 주소·사업자번호 같은 거래 안내 문구는 제외한다.
- 원문 그대로 옮긴다. 맞춤법을 고치거나 표현을 다듬지 마라.
  (붙여쓰기·특수문자·초성 같은 회피표기도 원문 그대로 둔다)
- 읽을 수 없는 글자는 그 문장을 통째로 빼지 말고 읽을 수 있는 부분만 담는다.
- 한국어가 전혀 없으면 빈 배열을 반환한다.

JSON으로만 답하라: {"sentences": ["문장1", "문장2"]}
```

이번 세션엔 로컬에 타일 이미지가 없어 새로 호출하진 않았다. 과거 실 스모크 기록(`PROGRESS_BE.md` 초기 항목,
Gemini 1회, `08_24505724_detail_007.png` 1타일): 6문장 추출, 이미지→타일→OCR 실동작 확인됨 — 그 결과를 그대로
인용한다(지어낸 값 아님, 다만 이번 세션에서 재실행한 건 아님).

배치(`BATCH_PROMPT`) 설계 이유: "한 요청에 이미지를 몰아넣으면 모델이 뒤쪽을 빠뜨리기 쉬우므로, 응답 개수가

명시, "이미지를 건너뛰지 마라")로 누락을 줄이려는 시도가 이미 들어가 있다.

## 4. 공통 설계 패턴 (프롬프트 엔지니어링 시 참고)

- **JSON 강제 출력**: 전 호출이 `"JSON으로만 답하라: {...}"` 형태로 스키마를 프롬프트에 박아 넣는다. OpenAI는
  `response_format={"type":"json_object"}` 추가 강제(일부 모델이 거부하면 자동으로 없이 재시도, `vlm.py:127`).
- **재시도 없음(과금 호출)**: 실패하면 그 배치/문장만 미판정·스킵으로 기록하고 계속 진행. CLAUDE.md E 원칙 그대로.
- **번호 매칭 + 개수 불일치 시 폴백 금지**: 판정·OCR 둘 다 응답을 순번으로 되짚는데, 개수가 안 맞으면(모델이
  항목을 빠뜨리거나 1-based로 셈) 위치 추정을 포기하고 안전 쪽(미판정/빈 배열)으로 떨어진다. 과거 이 부분에서
  프롬프트가 grounding으로 길어지자 모델이 종종 1-based로 세는 버그가 재현됐었다(`PROGRESS_BE.md` Phase3 기록).
- **provider 스왑은 코드 한 줄**: `get_vlm(provider)`가 어댑터를 고른다. 판정은 `JUDGE_PROVIDER`, 콘텐츠생성은
  `GENERATE_PROVIDER`(없으면 판정 provider 재사용), OCR은 `OCR_PROVIDER`. 프롬프트 자체는 provider 무관(같은
  텍스트를 Gemini/OpenAI 양쪽에 그대로 보냄).
- **그라운딩 온/오프는 얇은 스위치 하나**: `PromptJudge(vlm, context=...)`의 `context` 파라미터. 프롬프트
  엔지니어링할 때 이 값만 바꿔가며(빈 문자열 / `build_regulation_context()`만 / `build_judgment_context()`
  전체) A/B 비교하면 된다 — 판정 로직·JSON 스키마는 안 건드려도 됨.
