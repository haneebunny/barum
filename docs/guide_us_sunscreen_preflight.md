# 가이드: 미국 수출 프리플라이트 (자외선차단 최소보장)

> 목적: 수출 관련 백엔드 기능을 맡은 담당자가 순서대로 따라가며 작업할 수 있게 정리한 실행 가이드.
> 확정 결정(스코프·아키텍처)은 `2조_최종프로젝트_기획서_v1.9.docx`, 진행 상태는 `ROADMAP.md` 참조.
> 이 문서는 "무엇을 왜 하는지"까지 풀어서 설명한다 (비전공자 기준).

---

## 0. 이 기능이 뭔지 한 줄로

**한국 상품을 미국에 팔 때, "SPF" 표현이나 자외선차단 성분이 미국에서는 화장품이 아니라 의약품(OTC Drug)으로 취급되는지 미리 알려주는 기능.**

지금 국내 검증(`RagJudge`)이 하는 일과 똑같은 구조를 미국판으로 하나 더 만드는 거라고 보면 됩니다. **완전히 새로 짜는 게 아니라, 기존 틀에 미국 데이터만 갈아 끼우는 작업**이에요.

## 1. 지금까지 확정된 것 (다시 헤매지 않도록 정리)

| 항목 | 결정 | 근거 |
|---|---|---|
| 스코프 | **자외선차단(선크림)만.** 미백·주름은 이번 범위 아님 | 기획서 v1.6 "미국 프리플라이트 스코프를 자외선차단 최소보장으로 확정" |

## 2. 지금 코드가 어떻게 생겼는지 먼저 이해하기

새로 만들기 전에, **국내 판정이 어떤 파일들로 이루어져 있는지** 알아야 그대로 복제할 수 있어요. 아래가 국내(KR) 판정의 실제 구조입니다.

```
reference/cosmetic_kr/                          ← 사람이 읽는 정본 문서 (마크다운)
  ├─ functional_ingredients.md                   ← "이 성분 이 함량 이상이면 이 효능 주장 가능" 표
  ├─ prohibited_expressions.md                   ← 금지표현 목록 + 법조항
  ├─ citation_registry.md                        ← 법령/고시 원문 출처 등록부
  └─ violation_types/type_2_functional_misperception.md   ← 판정 규칙 서술

backend/src/barum/reference/
  ├─ data/functional_ingredients.json            ← 위 md를 코드가 읽을 JSON으로 변환한 것
  ├─ data/citation_registry.json
  ├─ ingredients.py                              ← JSON을 읽어서 "성분 있나 없나" 조회하는 코드
  ├─ citations.py                                ← 법령 인용 조회 코드
  └─ context.py                                  ← md 문서들을 통째로 모아 AI 프롬프트에 붙이는 코드

backend/src/barum/judge/cosmetic.py              ← 실제 판정 로직(RagJudge)이 위 조각들을 조합해 씀
```

**핵심 패턴**: 사람이 `.md`로 정본을 쓰고 → 코드가 읽을 `.json`으로 옮기고 → 조회 함수(`.py`)가 정확 대조를 한다. 미국판도 이 패턴을 그대로 복제하면 됩니다.

## 3. 작업 단계 (이 순서대로)

### 단계 1. 데이터 수집 — 원문을 직접 열어서 대조하기

**절대 하면 안 되는 것**: 웹서치 요약이나 블로그·뉴스 기사에 나온 성분표를 그대로 베끼는 것. 실제로 이번 작업 중에도 검색 요약본에 성분명이 부정확하게 섞여 나온 적이 있었다 (예: "Octyl methoxycinnamate"와 "Octinoxate"가 같은 성분인데 다른 이름처럼 보임 — 이건 오류가 아니라 CFR 공식명과 업계 통칭이 달라서다. 다만 확인 없이 베꼈으면 몰랐을 것).

**해야 하는 것**: 정본 문서 두 곳을 **직접 열어서** 대조한다.

1. **eCFR 21 CFR 352.10** (`www.law.cornell.edu/cfr/text/21/352.10` — ecfr.gov는 봇 차단이 있어 코넬 로스쿨 미러 사용) → **베이스라인 16종** 확인
2. **FDA 최종 오더 목록** (`accessdata.fda.gov`의 OTC Monographs@FDA 포털, 봇 차단 있으면 연방관보 `federalregister.gov` PDF로 원문 확보) → 베이스라인 이후 **개별 개정 오더**를 훑어서 추가/삭제된 성분이 있는지 확인

이번에 직접 대조한 결과 (2026-08-18 기준):

```markdown
# 미국 자외선차단 승인성분표

> 근거: eCFR 21 CFR 352.10 (M020 베이스라인, OTC000006으로 확정된 내용과 동일) + 개정 오더
> 확인일: 2026-08-18 (본문 원문 직접 대조 완료 — law.cornell.edu 미러, accessdata.fda.gov PDF)
> 갱신 방법: accessdata.fda.gov의 M020 오더 목록을 반기 1회 확인, 신규 오더 있으면 추가

## 베이스라인 (21 CFR 352.10, OTC000006)
| 성분명 (CFR 공식명) | 최대 함량 |
|---|---|
| Aminobenzoic acid (PABA) | 15% |
| Avobenzone | 3% |
| Cinoxate | 3% |
| Dioxybenzone | 3% |
| Homosalate | 15% |
| Menthyl anthranilate | 5% |
| Octocrylene | 10% |
| Octyl methoxycinnamate | 7.5% |
| Octyl salicylate | 5% |
| Oxybenzone | 6% |
| Padimate O | 8% |
| Phenylbenzimidazole sulfonic acid | 4% |
| Sulisobenzone | 10% |
| Titanium dioxide | 25% |
| Trolamine salicylate | 12% |
| Zinc oxide | 25% |

## 개정 오더로 추가된 성분
| 성분명 | 최대 함량 | 근거 오더 |
|---|---|---|
| Bemotrizinol | 6% | OTC000039 (최종오더, 연방관보 게재 2026-06-10, 원문 PDF 직접 확인) |
```

**아직 안 끝난 부분 (실제 작업 시 마저 확인할 것)**:
- OTC000006(2020) ~ OTC000039(2026) 사이에 다른 개정 오더가 더 있었는지, `accessdata.fda.gov` 포털의 M020 오더 전체 목록을 훑어서 빠짐없이 확인 필요 (이번엔 검색으로 걸린 것만 확인함 — 전체 목록 페이지가 봇 차단으로 못 열렸음)
- INCI명(화장품 전성분표 표기, 예: Ensulizole·Meradimate·Octinoxate·Octisalate)과 CFR 공식명이 다른 경우가 있어 **동의어 매핑표**가 필요함 (국내 판정의 `synonyms.json`과 같은 역할)

**왜 이 순서로 하나?**: 판정 로직을 아무리 잘 짜도 데이터가 틀리면 전부 틀린 답을 냄. 특히 이건 "미국 법적 분류를 알려주는" 기능이라 틀리면 사용자가 실제 수출 과정에서 낭패를 볼 수 있음 — 국내 판정보다 데이터 정확도 기준이 더 엄격해야 한다.

### 단계 2. 판정 규칙 문서 작성 — "언제 경고할지" 정하기

**할 일**: `violation_types/type_2_functional_misperception.md`를 본떠서, 미국 판정 로직을 사람이 읽는 문서로 먼저 정리합니다.

- 새 파일: `reference/cosmetic_us/sunscreen_otc_classification.md`
- 담을 내용 (기획서 시나리오 그대로):
  1. 문구에 **"SPF" 또는 자외선차단 표현**이 있는가? → 있으면 무조건 "미국에서는 화장품이 아니라 OTC 의약품" 경고
  2. 전성분 중 자외선차단 성분이 있는가? → 있으면 그 성분이 **단계 1의 승인 목록에 있는지** 대조
     - 목록에 있음 → "미국에서도 허용된 성분"
     - 목록에 없음 → "미국 FDA 미승인 성분" 경고 (지목)
     - 전성분 정보 자체가 없음 → "확인 불가, 성분 정보 추가 필요" 안내

이 단계는 **코드를 짜기 전에 로직을 말로 먼저 확정**하는 거예요. 국내 판정도 다 이렇게 먼저 md로 규칙을 쓰고 나서 코드로 옮겼습니다 (`type_2_functional_misperception.md`가 그 증거).

---

### 단계 3. JSON 데이터로 변환

**할 일**: 단계 1의 md 표를 코드가 읽을 수 있는 JSON으로 옮깁니다.

- 새 파일: `backend/src/barum/reference/data/us_sunscreen_ingredients.json`
- `functional_ingredients.json` 구조를 열어보고 똑같은 형식으로 만들면 됨 (성분명 → 최대함량 딕셔너리)

---

### 단계 4. 조회 코드 작성

**할 일**: `ingredients.py`를 본떠서 "이 성분이 미국 승인 목록에 있나 없나"를 확인하는 함수를 만듭니다.

- 새 파일: `backend/src/barum/reference/us_ingredients.py` (가칭)
- `ingredients.py`의 `match_ingredient()` 같은 함수를 참고해서, 성분명 하나 넣으면 승인 여부를 돌려주는 함수 작성
- 이건 AI(VLM) 호출 없이 **파이썬 코드로 정확 대조**하는 부분이라 비용도 안 들고 빠름 (국내 판정에서 성분 대조가 그렇듯이)

---

### 단계 5. 판정 로직 작성

**할 일**: `judge/cosmetic.py`의 `RagJudge`를 참고해서 미국판 판정기를 만듭니다.

두 가지 방식 중 하나를 고를 수 있어요 (여기서부턴 팀 인터뷰 필요):

- **A안**: 기존 `RagJudge`에 `region="US"`일 때 분기 추가 (같은 클래스, 국가별 로직만 분리)
- **B안**: `USSunscreenJudge`라는 새 클래스를 만들고, `region == "US"`일 때 이걸 호출

기획서의 "엔진은 하나, 레퍼런스 팩만 교체" 원칙을 보면 **A안이 원래 설계 의도에 더 가깝습니다.** 다만 지금 국내 판정 로직(규칙집→프리스크린→VLM)이 이미 복잡해서, 억지로 한 클래스에 우겨넣으면 코드가 지저분해질 수 있어요. 이 부분은 실제 코드를 보면서 팀과 상의하는 게 좋습니다.

---

### 단계 6. API 엔드포인트 연결

**할 일**: `api/app.py`에 새 엔드포인트를 추가합니다 (사용자가 "별도로 할 것"이라 확정한 부분).

- 예: `POST /check/export` 또는 `POST /check-us` (이름은 팀과 상의)
- 국내 `/check`와 비슷한 입력(이미지/텍스트/전성분)을 받되, 국가 파라미터를 받아 미국 판정기로 라우팅
- 기본값은 미국으로 (사용자 확정)

---

### 단계 7. 테스트

**할 일**: `tests/test_rag_judge.py`나 `test_reference_citations.py` 같은 기존 테스트 파일을 참고해서, 미국판 판정기 테스트를 작성합니다.

- 예시 케이스: "SPF50" 문구 + Avobenzone(승인) 성분 → 경고는 뜨되 성분은 안전
- 예시 케이스: "SPF50" 문구 + 한국 고시원료지만 미국 미승인 성분 → 경고 + 성분 지목

CLAUDE.md 규칙상 **순수 로직(성분 대조 같은 것)은 pytest 유닛테스트로**, VLM 호출이 들어가는 부분은 **수동 스모크 테스트**로 확인하면 됩니다.

## 4. 전체 흐름 그림

```
[단계1] M020 성분표 → md 문서 (사람이 읽는 정본)
   ↓
[단계2] 판정 규칙 → md 문서 (언제 경고할지 말로 정리)
   ↓
[단계3] md → JSON 변환 (코드가 읽을 수 있게)
   ↓
[단계4] JSON 조회 함수 (성분 있나 없나 확인)
   ↓
[단계5] 판정 로직 (SPF 표현 감지 + 성분 대조 조합)
   ↓
[단계6] API 엔드포인트 (프론트와 연결)
   ↓
[단계7] 테스트 (제대로 동작하는지 확인)
```

**왜 이 순서인가?**: 데이터(1~3단계)가 안 흔들려야 로직(4~5단계)이 안 흔들리고, 로직이 안정돼야 API(6단계)를 붙일 수 있어요. 거꾸로 API부터 만들면 나중에 데이터 바뀔 때마다 전체를 다시 손봐야 합니다.
